# 坐骑生产流程总纲

> 这份文档是「给游戏加一只新坐骑」的**唯一权威流程**。
>
> - 后端步骤目录：`backend/app/schemas/flow.py` 的 `FLOW_STEP_IDS`
> - 前端步骤目录：`apps/web/src/features/resources/lib/patch-flow.ts` 的 `PATCH_FLOW_STEPS`
> - 两者与本文各节标题一一对应（锚点见 §3），由 `backend/tests/unit/test_flow_steps.py` 断言防漂移
>
> 各特性的详细制作方法见 [坐骑特性附录](./02坐骑特性附录.md)。

---

## 1. 流程总览

### 1.1 九步主线

```
 ①筛选候选 ──▶ ②模型贴图就位 ──▶ ③编辑 YAML ──▶ ④补全官方数据
                                                      │
                                    ┌─────────────────┘
                                    ▼
                              ⑤预检（所见即所得）
                                    │
                                    ▼
 ⑥创建补丁任务 ──▶ ⑦构建补丁 ──▶ ⑧审查产物 ──▶ ⑨发布部署与验收
   [素材准备]        [编辑与预检]      [构建]      [审查与发布]
```

| # | 步骤 id | 标题 | 阶段 | 自动化 | 完成判据（可机器判定） |
|---|---|---|---|---|---|
| 1 | `select-candidates` | 筛选候选 | 素材准备 | 人工 | 候选坐骑 YAML 已存在于 `data/resources/mounts/` 且可被加载 |
| 2 | `stage-assets` | 模型贴图就位 | 素材准备 | 人工 | 资源目录存在且含 `.m2`；与贴图变体匹配的 `.blp` 非空；`model_folder` 纯 ASCII 无空格 |
| 3 | `edit-yaml` | 编辑 YAML | 编辑与预检 | 人工 | 8 项必填字段非空；`mount_type` 已选；`special_features` 在受控词表内 |
| 4 | `enrich-official` | 补全官方数据 | 编辑与预检 | 半自动 | `official_db.name` / `spell_wowhead_url` / `item_wowhead_url` 三者非空，或打 `no_official_data` 豁免 |
| 5 | `preflight` | 预检 | 编辑与预检 | **自动** | 4 条关联校验全 `ok`；DBC/SQL 计划可生成；唯一 ID 无重复；计划中的 DBC 记录 ID 未被源 DBC 占用 |
| 6 | `create-jobs` | 创建补丁任务 | 构建 | 自动 | 每个候选都有 `job.json` 且 `status == "requested"` |
| 7 | `build-patch` | 构建补丁 | 构建 | 自动 | `job.json` `status == "generated"`，`artifacts.output` 含 `mpq`/`sql_files`/`validation_report`/`audit` |
| 8 | `review-artifacts` | 审查产物 | 审查与发布 | 人工 | 校验报告中该任务的 error 级检查全 `passed`；审计报告含该任务的 DBC 字段级 before/after |
| 9 | `publish-deploy` | 发布部署与验收 | 审查与发布 | 人工 | `dist/{batch}/patch-zhCN-{N}.mpq` 存在；`job.status == "applied"`；YAML 的 `debug_passed` 与 `added` 均为 true |

### 1.2 状态字段语义（`added` / `debug_passed` 在第几步勾）

这两个布尔字段是**人工验收位**，全仓库没有自动回写路径，必须在资源详情页手工勾：

| 字段 | 含义 | 在第几步勾 |
|---|---|---|
| `debug_passed` | 客户端实测通过（模型显示正确、可召唤、特性符合预期） | 第 9 步，部署到测试服后 |
| `added` | 正式上线 | 第 9 步，客户端实测通过后 |

> 之前这两个字段在所有文档里都没有定义在流程的哪一步，导致「做完补丁就以为上线了」。
> 现在明确：**构建完成 ≠ 上线**。第 9 步的三个判据必须同时满足才算走完流程。

### 1.3 步骤状态从哪来

| 想知道 | 用什么 |
|---|---|
| 某只坐骑走到第几步了 | `GET /api/resources/mount/{id}/flow`（后端推导，前端只渲染） |
| 这次构建会写入什么 | `GET /api/patches/preview/mount/{id}`（第 5 步预检） |
| 界面上的步骤条 | 前端 `PATCH_FLOW_STEPS` 常量 |

## 2. 状态流转

### 2.1 补丁任务状态机

```
                    ┌──────────────┐
   patch export ───▶│  requested   │  已创建，未构建
                    └──────┬───────┘
                           │ patch build
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌──────────┐ ┌──────────┐  ┌─────────┐
        │ generated│ │  failed  │  │ applied │ ← patch publish
        └──────────┘ └────┬─────┘  └─────────┘
                          │ patch update <job_id> requested
                          └──────────▶ requested（可重跑）
```

| 状态 | 含义 | 谁写入 |
|---|---|---|
| `requested` | 已创建任务，未构建 | `patch export` / `export-request` |
| `generated` | 构建成功，产物已生成 | 构建器 |
| `failed` | 构建失败 | 构建器（异常分支） |
| `applied` | 已发布到 `workspace/dist/` | 发布器 |

> `applied` 与 `failed` 早期从未出现——发布器不写 job.json、构建失败也不写状态，
> 导致界面上分不清「构建失败」与「还没构建」。现已修复。

### 2.2 构建阶段（phase）

构建过程分 9 个阶段，界面实时显示当前阶段：

`load`（读取任务与计划）→ `validate`（检查 ID 冲突）→ `apply_dbc`（写入 DBC）→
`gen_sql`（生成 SQL）→ `build_mpq`（打包 MPQ）→ `report`（校验报告）→
`changelog`（变更日志）→ `audit`（审计报告）→ `finalize`（更新任务状态）

## 3. 逐步详解

<a id="step-1-select-candidates"></a>
### 3.1 第 1 步：筛选候选

**前置**：无（流程起点）

**操作**

1. 在资源列表页 `/resources?type=mount` 用筛选器挑出本批要做的坐骑：
   - 「状态」标签：`待调试` / `未添加` —— 挑还没上线的
   - 「星级」「类型」「特殊功能」标签 —— 挑本批目标范围内的
2. 每只候选坐骑都要有对应的 YAML 真相源。**没有 YAML 就没有后续步骤**：
   - 模型已就位但还没建 YAML 的，在 `data/resources/mounts/` 新建 `{id:04d}-{model_folder}.yaml`
   - YAML 结构照抄任意一只已完成的坐骑，字段含义见 [数据存储设计](../arch/02数据存储设计.md)

**产出物**：`data/resources/mounts/{id:04d}_*.yaml`

**完成判据**：`load_resource("mount", id)` 能返回该坐骑。

**对应入口**：Web 资源列表页 / CLI `uv run python -m app.cli resource list --type mount`

---

<a id="step-2-stage-assets"></a>
### 3.2 第 2 步：模型贴图就位

**前置**：第 1 步完成

**操作**

把模型与贴图放进 `sources/mounts/{model_folder}/`：

```
sources/mounts/ardenwealdstagmount影叶符文牡鹿/
├── ardenwealdstagmount/                 ← 模型子目录（部分资源包自带）
│   ├── ardenwealdstagmount.m2
│   ├── ardenwealdstagmount00.skin
│   ├── ardenwealdstagmount_blue.blp     ← 贴图变体，名字要与 YAML 里的 texture_variation 对上
│   └── ardenwealdstagmount0061-00.anim
└── 梦光符文牡鹿.png                      ← 预览图（可选，用于多模态识别）
```

- `.m2` / `.skin` / `.blp` / `.anim` 会打进 MPQ；`.png` / `.gif` 只用于预览，不会打包。
- 图标放 `sources/icons/interface/icons/{icon_name}.blp`，名字要与 YAML 的 `official_db.icon_name` / `spell_icon_name` 一致。
- 模型素材可从 wago.tools 拉取：`uv run python -m app.cli wago search "..."`、`uv run python -m app.cli wago download ...`

**产出物**：`sources/mounts/{model_folder}/**`

**完成判据**：资源目录存在、含至少 1 个 `.m2`、与 `texture_variation_*` 匹配的 `.blp` 非空。

**常见问题**

- **贴图变体匹配不到**：贴图文件名必须**包含**变体名（忽略大小写）。`texture_variation_1: ardenwealdstagmount_blue` 需要 `ardenwealdstagmount_blue.blp` 这样的文件。
- **`model_folder` 含中文**：不影响使用，构建时 `sanitize_model_folder()` 会自动转成纯英文路径。但路径里不要有**空格**——空格会导致 MPQ 内路径异常。

**对应入口**：Web 资源详情页「模型预览」 / CLI `uv run python -m app.cli wago --help`

---

<a id="step-3-edit-yaml"></a>
### 3.3 第 3 步：编辑 YAML

**前置**：第 2 步完成

**操作**

在 Web 资源详情页填写，或直接编辑 YAML。必填字段（8 项，导出时不会自动补默认值）：

| 字段路径 | 含义 |
|---|---|
| `dbc.spell.id` | 召唤法术 ID（80000 段） |
| `dbc.creature_model_data.id` | 模型数据 ID（4000 段） |
| `dbc.creature_model_data.model_name` | 模型路径，如 `creature\ardenwealdstagmount\ardenwealdstagmount.m2` |
| `dbc.item.id` | DBC 物品 ID（91000 段） |
| `db.creature_template.entry` | 挂载生物 entry（9140000 段） |
| `db.creature_template.name` | 生物名称 |
| `db.item_template.entry` | 物品 entry |
| `db.item_template.name` | 物品名称 |

**ID 段位规划**（全局唯一，冲突会被构建器拒绝）：

| 表 | 段位 |
|---|---|
| `CreatureModelData.ID` | 4000+ |
| `CreatureDisplayInfo.ID` | 140000+ |
| `Spell.ID` | 80000+ |
| `Item.ID` / `item_template.entry` | 91000+ |
| `creature_template.entry` | 9140000+ |
| `Vehicle.dbc`（自建载具） | 90000+ |

**关键约束**

- `dbc.spell.visual_id` **必须等于** `db.creature_template.entry`。
  服务端 `HandleAuraMounted` 是拿 `Spell.dbc` 的 `EffectMiscValue_1` 当 `creature_template.entry`
  去查生物模板取显示模型的——法术本身不携带 display id。
- `special_features` 的取值必须落在受控词表内（见 [特性附录](./02坐骑特性附录.md)），
  词表外的值会被后端**静默丢弃**。

**产出物**：更新后的 `data/resources/mounts/{id:04d}_*.yaml`

**完成判据**：8 项必填字段非空 + `mount_type` 已选 + 特性取值合法。

**对应入口**：Web 资源详情页 / CLI `uv run python -m app.cli resource update --type mount --id 3 --field official_db.name=新名称`

<a id="step-4-enrich-official"></a>
### 3.4 第 4 步：补全官方数据

**前置**：第 3 步完成

**操作**

补全官方名称、图标名与 Wowhead 链接：

```bash
cd backend
uv run python -m app.cli wowhead lookup-mount "梦光符文牡鹿"
```

Web 端也可以在资源详情页触发 Wowhead 查询（异步，浏览器会起 Playwright，耗时数十秒）。

反查图标对应的 SpellIcon ID（填入 `dbc.spell.icon_id`）：

```bash
uv run python -m app.cli dbc icon-id "inv_ardenwealdstagmount_blue"
```

**产出物**：YAML 的 `official_db` 块

**完成判据**：`official_db.name`、`spell_wowhead_url`、`item_wowhead_url` 三者非空；
确实没有官方数据的坐骑打 `no_official_data` 标签豁免。

**常见问题**

- **Wowhead 返回的名字和图片识别的不一致**：停下人工裁决，不要盲目写入。
  零售版和 WotLK 的同名坐骑容易混淆。
- **`dbc.item.display_id` 查不到**：Wowhead 不提供这个字段，要自己查 `ItemDisplayInfo.dbc`。

<a id="step-5-preflight"></a>
### 3.5 第 5 步：预检（所见即所得）

**前置**：第 4 步完成

**操作**

在创建补丁任务之前，预览「这次构建会往 DBC/SQL 写入什么」，并把问题一次列清：

```bash
curl -s http://localhost:8000/api/patches/preview/mount/3 | python3 -m json.tool
```

Web 端在资源详情页「补丁预检」卡片里直接看。

**预检会检查**

| 检查 | 判定 |
|---|---|
| 关联一致性 | 4 条规则（法术↔物品、模型↔显示、显示↔生物模板、entry↔视觉）是否全 `ok` |
| 计划可生成 | `build_dbc_plan` / `build_sql_plan` 能否跑通（特性冲突会在此暴露） |
| ID 唯一性 | 8 个全局唯一 ID 字段有没有和别的坐骑撞号 |
| DBC 占用 | 计划中的记录 ID 是否已被源 DBC 占用（占用则构建时会**跳过不覆盖**） |
| 资源就位 | `.m2` 是否存在、贴图变体是否匹配、`model_folder` 是否需要清理 |

**产出物**：预览结果（**不落盘**，纯内存计算）

**完成判据**：`ready == true`（无 error 级问题）。

> **与 dry-run 的区别**：dry-run（`patch build --dry-run`）需要先有任务（第 6 步），
> 会往 `workspace/patch-jobs/*/plans/` 落盘；本步在创建任务之前，只在内存里算。

<a id="step-6-create-jobs"></a>
### 3.6 第 6 步：创建补丁任务

**前置**：第 5 步通过

**操作**

```bash
cd backend
uv run python -m app.cli patch export --type mount --id 3
```

或批量（Web 端在资源列表页或导出向导第一步做同一件事）。

**Web 端**：资源列表页勾选坐骑 → 「创建补丁任务 (N)」→ 成功面板直接给出
「前往构建补丁」按钮，跳到 `/export?jobs=...` 并自动进入构建步骤。
**这一步只是流程的第 6 步，界面不能在这里断掉**——创建完必须能直接进入构建。

**产出物**：`workspace/patch-jobs/mount_0003/job.json`

**完成判据**：每个候选都有 `job.json` 且 `status == "requested"`。

**常见问题**

- **重复导出会重置任务目录**：`create_patch_job` 会清空已有的任务目录，
  丢失已构建的产物路径记录。已构建过的坐骑不要重复导出，除非确实要重建。
- **任务 ID 规则**：`{资源类型}_{资源ID 四位补零}`，例如 `mount_0003`。这是全流程的锚点。

---

<a id="step-7-build-patch"></a>
### 3.7 第 7 步：构建补丁

**前置**：第 6 步完成

**操作**

```bash
# 先干跑校验（只落盘计划，不改源文件）
uv run python -m app.cli patch build --jobs mount_0003 --dry-run

# 审查通过后正式构建
uv run python -m app.cli patch build --jobs mount_0003
```

全量重建：`uv run python -m app.cli patch build --all-requested --force`
（`--force` 会按计划强制重写已存在的 DBC 记录，SQL 跳过历史条目检查——**慎用**）。

**产出物**

| 产物 | 路径 |
|---|---|
| 编辑后的源 DBC | `data/wow-dbc/src/dbc/*.dbc` |
| SQL 补丁 | `data/sql/azerothcore-updates/mounts/{id:04d}_{model_folder}/*.sql` |
| 客户端补丁包 | `workspace/mpq/{batch}/patch-mounts.mpq` |
| 校验报告 | `workspace/reports/{batch}/validation-report.json` |
| 审计报告 | `workspace/reports/{batch}/audit-report.json` |

**完成判据**：`job.json` `status == "generated"`，且 `artifacts.output` 四个键齐全。

**Web 端的构建范围与选项**

构建步骤只有三个可调项，每个都写明了影响：

| 选项 | 含义 | 影响 |
|---|---|---|
| 构建范围 | 本次选中的 N 只 / 全部待处理任务 | 「全部」会重建工作区里所有未发布任务的 DBC 记录，数量大时界面会给出警告 |
| 先试运行（默认开） | 只检查 ID 冲突并把计划写进任务目录 | **不修改任何源文件**，确认计划无误后再取消勾选正式构建 |
| 高级选项 → 覆盖已存在的 DBC 记录 | 按计划强制重写已存在的记录，且不再生成新的 SQL 补丁 | 仅用于「记录写错了要重来」；勾选后界面显示红色警告 |

> 「全部待处理任务」与「覆盖已有 DBC 记录」都是**破坏性操作**，
> 因此前者用单选而非复选、后者收在折叠的高级选项里——避免被当成无害选项误触。

**幂等性：重复创建任务不会破坏已有构建记录**

对一只**已经构建过**的坐骑再次点「创建补丁任务」，任务的 `status` 与
`artifacts`（产物路径登记）会**原样保留**，只刷新资源快照字段。
早期实现是无条件删除任务目录重建，会把 `generated` 退回 `requested`、
清空产物登记——产物还在磁盘上但登记丢了，审查步骤就再也读不到校验报告。

即使登记丢失，读取校验报告与产物清单时也会**回退到批次报告**反查该任务，
不会因为一次重复创建就看不到已构建的结果。

**常见问题**

- **DBC ID 冲突**：构建器直接拒绝。说明两只坐骑用了同一个 ID，回到第 3 步改。
- **构建失败**：任务的 `status` 会被写成 `failed`，`summary` 里带原因。
  修好后 `uv run python -m app.cli patch update mount_0003 requested` 改回 `requested` 再重跑。
- **构建不写 git**：`data/wow-dbc` 是子模块，改动需要手动提交（见 §8）。
- **日志里一长串任务**：Web 端会把任务清单折叠成一行「展开 N 个坐骑」，
  展开后每行是「任务 ID + 坐骑名」。CLI 仍输出完整清单。

<a id="step-8-review-artifacts"></a>
### 3.8 第 8 步：审查产物

**前置**：第 7 步完成

**操作**

逐条看校验报告，确认将要落库/落客户端的内容：

```bash
# 批次级报告
cat workspace/reports/{batch}/validation-report.json

# 单任务切片
curl -s http://localhost:8000/api/patches/jobs/mount_0003/validation-report | python3 -m json.tool

# 字段级审计（DBC before → after）
uv run python -m app.cli patch audit mount_0003
```

Web 端在导出向导第三步「审查产物」里可以按任务展开校验报告、查看产物清单并直接下载。

**产出物**：人工审查结论

**完成判据**：该任务的 **error 级**检查全部 `passed`；审计报告里能看到 DBC 字段的 before/after。

**常见问题**

- **warning 级不阻塞发布**：例如「`model_folder` 含中文，已自动清理」是提示性的。
  但「模型路径在 MPQ 内不存在」这类必须查清楚。

<a id="step-9-publish-deploy"></a>
### 3.9 第 9 步：发布部署与验收

**前置**：第 8 步通过

**操作**

**发布**：

```bash
uv run python -m app.cli patch publish --batch 20261121_114744 --start-number 7
uv run python -m app.cli patch publish --batch 20261121_114744 --dry-run   # 只预览
```

发布是**移动语义**：MPQ 从 `workspace/mpq/{batch}/` 移到 `workspace/dist/{batch}/`
并重命名为客户端可识别的 `patch-zhCN-{N}.mpq`。发布成功后该批任务的 `status`
变为 `applied`。

**「发布」与「推送到分发端」是两个独立动作**：

| 动作 | 做什么 | 可否撤销 | 谁受影响 |
|---|---|---|---|
| ① 本地发布 | 改名 + 移到 `workspace/dist/` | 可（把文件移回去） | 只有自己 |
| ② 推送到分发端 | 上传到 acore-patch-distro | **不可撤销** | 玩家可下载、公告同步发布 |

推送是一次**不可逆的对外动作**，因此必须显式触发，不能藏在发布里。

**推送成功后自动清理本地 MPQ 副本**：分发端才是玩家下载的来源，本地再留一份
就是双份存储（单个补丁 300MB+）。批次元数据（manifest / changelog / readme）
保留，供审计与批次列表使用。**推送失败时本地副本必须保留**——那是重试的唯一来源。

手动清理在 `/mpq` 页：档案列表每个条目有删除按钮，只删 MPQ 文件本体，
元数据保留；引用该批次的补丁任务会退回「待构建」。

```bash
# ① 本地发布
uv run python -m app.cli patch publish --batch 20261121_114744 --start-number 7

# ② 推送到分发端（需要玩家可下载时才做）
uv run python -m app.cli patch distro-push --batch 20261121_114744
```

对应 API：`POST /api/patches/publish`（本地发布）、`POST /api/patches/distro-push`（推送）、
`GET /api/patches/distro/status`（本地已发布 vs 分发端已推送的对照）。

**从分发端下线**：分发端提供了 admin 管理接口，推送端可远程删除批次
（`DELETE /api/patches/distro/batches/{batch}`），也可以只改元数据而不重传 MPQ
（`PATCH /api/patches/distro/batches/{batch}`，如更正 changelog）。
「改元数据」不影响批次可见性——这与 announce 的语义不同：announce 会把批次
打回 pending 从而从列表消失。`GET /api/patches/distro/batches` 能看到
分发端的全部批次（含 announce 后没上传成功的 pending 残留）。

> ⚠️ **一定要带 `--batch` 指定批次**。不带时会发布 `workspace/mpq/` 下的
> **所有**未发布批次，其中可能夹带含旧 DBC 的历史批次——客户端按编号顺序加载，
> 旧 DBC 会把新 DBC 覆盖回去。
>
> 干跑会返回 `preview` 字段，如实列出「将发布哪个批次、编成几号」。
> 早期实现干跑时 `published` 恒为空，界面只能显示「没有找到可发布的批次」，
> 把预览误报成失败——发布流程因此被误判为「没走完」。

**部署**（三处，缺一不可；推送分发端是第四件、但可后置）：

| 目标 | 操作 |
|---|---|
| 服务端 SQL | `data/sql/azerothcore-updates/mounts/{id}/*.sql` → `acore_world`（该目录是 AzerothCore updates 目录的软链，worldserver 重启即加载） |
| 客户端 MPQ | `workspace/dist/{batch}/patch-zhCN-{N}.mpq` → 客户端 `World of Warcraft/Data/` |
| DBC | `bash acore-deploy/scripts/acore-update-dbc.sh --local-path data/wow-dbc/src/dbc` |

首次加载新 MPQ 要清客户端 `Data/cache/` 并重启客户端。

**验收**：

在资源详情页勾选「调试通过」与「已添加」，保存。
导出向导的完成页会把这三步（部署服务端 / 部署客户端 / 实测并标记）列成清单，
并给出「去资源列表勾选『调试通过』」的直达入口。

**产出物**：`workspace/dist/{batch}/patch-zhCN-{N}.mpq`、资源状态位

**完成判据**：

1. `workspace/dist/{batch}/patch-zhCN-{N}.mpq` 存在
2. `job.json` `status == "applied"`
3. YAML 的 `debug_passed == true` 且 `added == true`

## 4. 自动化程度矩阵

| 步骤 | CLI | HTTP API | Web UI |
|---|---|---|---|
| 1 筛选候选 | `resource list` | `GET /api/resources/mount` | `/resources?type=mount` 筛选器 |
| 2 模型贴图就位 | `wago search/download` | `GET /api/preview/model/{folder}` | 资源详情页模型预览 |
| 3 编辑 YAML | `resource update` | `PUT /api/resources/mount/{id}` | 资源详情页表单 |
| 4 补全官方数据 | `wowhead lookup-mount`、`dbc icon-id` | `POST /api/wowhead/search` | 资源详情页（异步查询） |
| 5 预检 | — | `GET /api/patches/preview/mount/{id}` | 资源详情页「补丁预检」 |
| 6 创建补丁任务 | `patch export` | `POST /api/patches/export-request` | 资源列表页「创建补丁任务」，或导出向导第 1 步 |
| 7 构建补丁 | `patch build` | `POST /api/patches/build` + `GET /build/status` | 导出向导第 2 步 |
| 8 审查产物 | `patch audit` | `GET /api/patches/jobs/{id}/validation-report`、`.../audit`、`.../artifacts` | 导出向导第 3 步 |
| 9 发布部署 | `patch publish`、`patch distro-push` | `POST /api/patches/publish` | 导出向导第 4 步 |

### 4.1 Web UI 的两条动线

界面上的流程**不允许出现断头路**——每一步做完后都要能直接进入下一步：

**动线 A：从资源列表开始（批量）**

```
/resources?type=mount
  → 勾选坐骑（工具栏实时显示已选数量与名称）
  → 「创建补丁任务」按钮 → 弹出对话框
       ├ 确认态：逐只列出坐骑 + 预检结果（预检通过 / N 个错误）
       │           有问题时明确列出缺哪些必填字段
       └ 成功态：✓ 已创建 N 个任务 + 任务 ID +「继续构建补丁 →」
  → /export?jobs=mount_0003,mount_0004   ← 自动进入构建步骤
  → 构建 → 审查产物 → 发布补丁
  → 完成页：部署服务端 / 部署客户端 / 实测并勾选标记（3 步清单）
```

**动线 B：从导出页开始（向导内自选）**

```
/export
  → 顶部流程上下文条（9 步全貌，①~⑤ 已完成带勾，⑥~⑨ 可点击跳转）
  → 选择坐骑 → 创建补丁任务 → 构建 → 审查 → 发布
```

**界面约定**

- **步骤指示器只有一处**：页面顶部的流程上下文条。向导内部不再重复画一遍。
- **不做断头路**：任何一步做完后，界面上都必须有明确的「下一步」入口。
- **过程可观测**：创建前就能看到每只坐骑的预检结果；构建时显示阶段与进度；
  构建后能逐项查看校验报告与产物清单。
- **列表页是流程状态的入口**：每只坐骑带一个「补丁任务」徽标
  （`—` / `待构建` / `已构建` / `已发布` / `构建失败`），
  不用进详情页就知道它走到了哪一步。
- **多余补丁在 `/mpq` 页清理**：档案列表每个条目有删除按钮，
  确认对话框会说明「删什么、会不会影响玩家、哪些任务被退回待构建」。
  已推送到分发端的补丁会额外警告——删的只是本地副本，
  并提供「同时从分发端删除」勾选项，避免两边状态漂移。
- **「仅在分发端」的批次不会消失**：推送成功后本地 MPQ 会被清理，
  这类补丁在本地档案列表里看不到，但玩家仍能下载到。
  `/mpq` 页因此单列一个「分发端批次」清单，逐条标出
  「玩家可下载 / 不可见（残留）」与「本地副本已清理 / 本地仍有副本」，
  每条都能直接从分发端下线。

**相关 API**

| 用途 | 端点 |
|---|---|
| 单只预检 | `GET /api/patches/preview/mount/{id}` |
| 批量预检（对话框用，DBC 只加载一次） | `POST /api/patches/preview/batch` |

### 4.2 批次列表是操作中心

`/export` 页底的「补丁批次列表」不只是查看用的——它是对**已构建批次**做操作的地方：

| 层级 | 操作 | 说明 |
|---|---|---|
| 批次 | 校验报告 | 打开该批次的字段级校验报告 |
| 批次 | 重建 | 弹窗选择「先试运行」或「正式构建」，**只处理这批坐骑**，不影响其它待处理任务 |
| 批次 | 发布 | 只发布这一个批次（本地发布，不推送） |
| 批次 | 推送到分发端 | 独立按钮；推送不可撤销，界面有明确警告 |
| 批次 | 删除 | 删除该批次下的全部任务（不影响真相源与已生成产物） |
| 任务 | 校验 / 审计 / 详情 / 删除 | 单个任务的校验报告、字段级审计、跳资源详情页、删除 |
| 产物 | 路径即链接 | 补丁包、批次清单、变更日志、校验报告、审计报告、SQL 文件都可点击打开 |

对应的 CLI：

```bash
uv run python -m app.cli patch publish --batch 20261121_013605   # 只发布指定批次
uv run python -m app.cli patch publish --dry-run                  # 预览全部
```

## 6. 失败处理与回滚

| 情况 | 处理 |
|---|---|
| 构建失败 | 任务被标记 `failed`；修好后 `patch update {job_id} requested` 再重跑 |
| DBC 写错了 | 用 `git -C data/wow-dbc checkout -- src/dbc/*.dbc` 回滚源 DBC，重新构建 |
| SQL 生成错了 | 删掉 `data/sql/azerothcore-updates/mounts/{id}_{slug}/` 后 `--force` 重建 |
| MPQ 打错了 | 删掉 `workspace/mpq/{batch}/` 后重新构建 |
| 发布了但想撤回 | `workspace/dist/{batch}/patch-zhCN-{N}.mpq` 删掉即可（客户端需清缓存重启） |
| 任务状态乱了 | `patch update {job_id} requested` 重置；`patch delete {job_id}` 删任务目录 |
| 工作区太大 | `/export` 页「清理工作区」或 `patch clean`（默认只预览，`--execute` 才真删） |

## 7. 故障排查速查表

| 现象 | 原因 | 处理 |
|---|---|---|
| 客户端看不到新坐骑 | MPQ 没拷到客户端 `Data/`，或没清 `Data/cache/` | 重新拷贝 + 清缓存 + 重启客户端 |
| 召唤出来是别的模型 | `dbc.spell.visual_id` ≠ `db.creature_template.entry` | 第 5 步预检会报 `entry_visual` 不一致 |
| 坐骑能召唤但没有模型 | `dbc.creature_model_data.model_name` 指向的 `.m2` 没进 MPQ | 第 5 步预检的「模型路径与 MPQ 内实际文件一致」 |
| 贴图是默认的 | `texture_variation_*` 与磁盘上的 `.blp` 文件名对不上 | 第 2 步确认贴图变体命名 |
| 导出时报「第一阶段仅支持 mount 类型」 | 非坐骑资源 | 宠物/NPC 尚未管线化，见 §9 |
| 构建报 DBC ID 冲突 | 两只坐骑用了同一个 ID | 第 3 步换 ID 段位 |
| 界面看不到构建进度 | 构建状态在内存里，进程重启会丢 | 重新触发构建 |

## 8. Git / 子模块提交清单

按顺序提交，**不要漏掉子模块**：

```bash
# 1. 资源定义（YAML 真相源）
git add data/resources/mounts/*.yaml
git commit -m "data(mounts): 更新坐骑元数据"

# 2. DBC 子模块（独立仓库）
cd data/wow-dbc
git add src/dbc/*.dbc
git commit -m "chore(dbc): add custom mount records"
cd ../..

# 3. 服务端 SQL（在 AzerothCore 仓库，本仓库只存软链）
cd /path/to/azerothcore-wotlk
git add modules/mod-custom-content/data/sql/db-world/updates/
git commit -m "feat(sql): add custom mount rows"
```

> `workspace/`（任务目录、MPQ 批次、报告）**不入 Git**。

# 数据存储设计

## 一、数据存储技术栈

| 技术栈 | 版本 | 说明 |
|-------|------|------|
| **YAML/JSON 文件** | - | 资源定义主存储，纳入 Git 版本控制 |
| **SQLite** | 3.40+ | 运行时缓存（按需写入），支持快速查询和筛选 |
| **原始 `.xlsx`** | - | 一次性导入源（约 730MB+），不纳入 Git |
| **Pydantic 模型** | 2.5+ | `backend/app/schemas/` 下定义 DBC/SQL/Resource 的字段类型与归一化规则 |
| **SQLAlchemy ORM** | 2.0+ | `backend/app/models/resource.py` 中 `ResourceMixin + Mount/Pet/Npc`，将原始 YAML 文本存入 `raw_yaml` 列 |
| **图片资源** | - | `sources/mounts/`、`sources/pets/`、`sources/npcs/`、`sources/icons/`，通过文件系统访问 |

> **真相源说明**：YAML 是唯一真相源，SQLite 仅用于运行时加速查询；两者通过 `resource_store.save_resource()` 在保存时同步。`registry.json` 由系统自动生成，Agent 不直接修改。

## 二、存储分层

| 层级 | 存储形式 | 职责 | 是否入 Git |
|------|---------|------|:----------:|
| **资源定义层** | `data/resources/{mounts,pets,npcs}/*.yaml` | 单资源完整定义，人类可读，Agent 可操作 | ✅ |
| **资源索引层** | `data/registry.json` | 资源快速索引和状态汇总（counts + 列表） | ✅ |
| **映射配置层** | `data/mapping/{mount,pet,npc}.mapping.yaml` | `.xlsx` 列号到字段名的映射 | ✅ |
| **DBC 真相源** | `data/wow-dbc/src/dbc/*.dbc` | 原始 DBC 文件（git 子模块，上游 `domonic18/wow-dbc`） | ✅（子模块） |
| **生成的 SQL** | `data/sql/azerothcore-updates/*.sql` | `patch build` 直接写入的 AzerothCore SQL 补丁 | ✅（软链接除外） |
| **运行时层** | `workspace/data/acore_resource.db`（SQLite） | 运行时查询、筛选、统计 | ❌ |
| **导入源层** | `imports/*.xlsx` | 一次性导入源 | ❌ |
| **图片资源层** | `sources/mounts/`、`sources/pets/`、`sources/npcs/`、`sources/icons/` | 预览图和原始模型/贴图/图标 | ❌ |
| **缩略图缓存层** | `workspace/assets/thumbnails/` | BLP → WebP 缩略图，可安全删除 | ❌ |
| **补丁任务层** | `workspace/patch-jobs/{job_id}/` | 单资源的补丁原料 + 产物 | ❌ |
| **MPQ 批次层** | `workspace/mpq/{batch}/`、`workspace/dist/` | 批次 MPQ 与已发布的 `patch-zhCN-N.mpq` | ❌ |

## 四、资源定义文件结构

> 字段定义以 `backend/app/schemas/` 下的 Pydantic 模型为准：`resource.py` 定义资源主体，`dbc.py` / `sql.py` 定义 DBC/SQL 子结构。所有可选字段允许为 `null`；空字符串 / `0`（仅对 `str | None` 字段）会在 `model_validator(mode="before")` 中归一化为 `None`，兼容旧 YAML 与 Excel 数据。

### 4.2 宠物 / NPC YAML 结构

宠物 / NPC 复用 `ResourceBase`，差异在于：

- 不包含 `mount_type` / `star_rating` / `subtype`。
- 改用 `rarity` 表达稀有度（例如 `三星`）。
- 字段集合与坐骑的 `dbc` / `db` 子结构完全一致，便于后续补丁生成器复用。

```yaml
id: 1
model_folder: agronn兽人猪NPC
preview_image: null
debug_passed: false
added: false
rarity: null
official_db:
  name: null
  spell_icon_name: null
  icon_name: null
  spell_wowhead_url: null
  item_wowhead_url: null
dbc: { ... }   # 字段结构同坐骑
db:  { ... }
```

### 4.3 标签与"无官方数据"

当某条资源经 Wowhead / wago.tools 查询后确认不存在官方数据时，会在 `tags` 字段中追加 `no_official_data` 标签（由 `enrich-mount-data` / `enrich-pet-data` Skill 写入），此时 `official_db.name` 允许为空，校验器会跳过名称必填检查。

```yaml
tags:
  - no_official_data
```

### 4.4 资源索引 registry.json

由后端在保存资源时同步生成，前端仪表盘与 CLI 列表均会优先读取：

```json
{
  "version": "1.0",
  "counts": {
    "mounts": 451,
    "pets": 107,
    "npcs": 226
  },
  "mounts": [
    {
      "id": 3,
      "name": "梦光符文牡鹿",
      "model_folder": "ardenwealdstagmount影叶符文牡鹿",
      "file": "data/resources/mounts/0003-ardenwealdstagmount影叶符文牡鹿.yaml",

      "added": true

  "npcs": [ /* ... */ ]

```

> Agent 不应直接修改 `registry.json`；任何字段变更应通过 `resource update` 或写 YAML 文件，由系统在下一次保存时重建索引。

## 五、数据库表设计（SQLite 缓存层）

> **重要**：SQLite 仅作为 YAML 的运行时缓存视图。当前实现没有为 DBC/SQL 字段建立独立关系表——这些字段全部存放在资源的 `raw_yaml` 文本中，由 Pydantic 模型按需反序列化。下表描述的是当前 `backend/app/models/resource.py` 中通过 `ResourceMixin` 实际定义的 ORM 结构。

### 5.1 资源表（每类资源一张）

由 `ResourceMixin` 派生得到 `mounts` / `pets` / `npcs` 三张表，结构完全一致：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | INTEGER PK | 资源唯一 ID |
| `model_folder` | VARCHAR | 模型文件夹名（索引） |
| `preview_image` | VARCHAR NULL | 预览图相对路径 |
| `debug_passed` | BOOLEAN | 调试通过 |
| `added` | BOOLEAN | 已添加 |
| `raw_yaml` | TEXT NOT NULL | 完整 YAML 文本（含 `dbc` / `db` 子结构） |

`Mount` 表额外包含 `mount_type` / `star_rating` / `subtype`；`Pet` / `Npc` 表额外包含 `rarity`。这些"扩展字段"用于列表筛选和排序；其余 DBC/SQL 字段一律从 `raw_yaml` 解析得到。

### 5.2 DBC / SQL 字段的 Pydantic 投影

DBC / SQL 表不出现在 SQLite 中，但通过 `app/schemas/dbc.py`、`app/schemas/sql.py` 提供类型安全的访问：

| DBC 文件 | Pydantic 模型 | 关键字段 |
|----------|---------------|---------|
| `CreatureModelData.dbc` | `CreatureModelData` | `id`, `flags`, `model_name`, `model_scale`, `collision_width/height`, `mount_height` |
| `CreatureDisplayInfo.dbc` | `CreatureDisplayInfo` | `id`, `model_id`, `sound_id`, `scale`, `opacity`, `texture_variation_1/2/3`, `creature_geoset_data` 等 |
| `Spell.dbc` | `Spell` | `id`, `visual_id`, `icon_id`, `name`, `description` |
| `Item.dbc` | `Item` | `id`, `class` (别名 `class_`), `subclass`, `material`, `display_id`, `inventory_type`, `sheath` |

| AzerothCore 表 | Pydantic 模型 | 关键字段 |
|----------------|---------------|---------|
| `creature_template` | `CreatureTemplate` | `entry`, `name`, `modelid1`, `faction`, `type`, `unit_class`, `unit_flag2`, `bounding_radius`, `combat_reach`, `gender`, `display_id_other_gender` |
| `creature_model_info` | `CreatureModelInfo` | `display_id`, `bounding_radius`, `combat_reach`, `gender`, `display_id_other_gender` |
| `item_template` | `ItemTemplate` | `entry`, `name`, `displayid`, `spellid_1/2`, `spelltrigger_1/2`, `Quality`, `AllowableClass`, `AllowableRace` 等 |

所有模型基类都包含一个 `model_validator(mode="before")` 钩子，会将空字符串和 `0`（仅对 `str | None` 字段）归一化为 `None`，从而兼容历史 YAML 与 Excel 中的占位值。

### 5.3 变更历史与预览缓存

- 当前实现 **未启用** `change_logs` 表；变更追溯依赖 Git 历史。
- 缩略图缓存通过文件系统（`workspace/assets/thumbnails/`）+ 文件 mtime 比对实现，未持久化到数据库。如未来需要 LRU 清理或跨进程共享，可再引入 `preview_cache` 表。

## 六、ID 关联关系

`backend/app/services/resource_validation.py` 中的 `MOUNT_RELATIONSHIPS` 定义了坐骑的跨数据源关联规则，资源保存与 `validate` 命令都会执行这些检查：

```
┌─────────────────────────────┐
│        Resource 记录         │
│   (坐骑/宠物/NPC)            │
└─────────────┬───────────────┘
              │
      ┌───────┼───────┐
      ▼       ▼       ▼
┌─────────┐ ┌─────────┐ ┌─────────┐
│Creature │ │  Spell  │ │  Item   │
│Display  │ │  .dbc   │ │  .dbc   │
│Info     │ │         │ │         │
└────┬────┘ └────┬────┘ └────┬────┘
     │           │           │
     │ ModelID   │ visual_id  │ display_id
     ▼           │           │
┌─────────┐      │           │
│Creature │◄─────┘           │
│Model    │                   │
│Data     │                   │
└─────────┘                   │
                              ▼
                        ┌─────────┐
                        │ item_   │
                        │ template│
                        └─────────┘

数据库侧：
creature_template.entry  ───┐
spell.visual_id             ├─►  必须一致（rule: entry_visual）
creature_template.modelid1 ─┐│
creature_model_info.display_id ─┴─►  必须等于 CreatureDisplayInfo.ID
                                     （rule: display_template_info）
creature_model_data.id  ─────►  必须等于 CreatureDisplayInfo.model_id
                                     （rule: model_display）
spell.id  ◄─────── item_template.spellid_2   （rule: spell_item）
```

四条核心规则：

| 规则 key | 名称 | 字段集合 |
|----------|------|---------|
| `spell_item` | Spell ↔ Item | `dbc.spell.id` ↔ `db.item_template.spellid_2` |
| `model_display` | Model → Display | `dbc.creature_model_data.id` ↔ `dbc.creature_display_info.model_id` |
| `display_template_info` | Display ↔ Template ↔ ModelInfo | `dbc.creature_display_info.id` ↔ `db.creature_template.modelid1` ↔ `db.creature_model_info.display_id` |
| `entry_visual` | Entry ↔ Visual | `db.creature_template.entry` ↔ `dbc.spell.visual_id` |

此外，`check_duplicate_resource_ids()` 会扫描所有坐骑的 `dbc.spell.id` / `dbc.item.id` / `dbc.creature_display_info.id` / `dbc.creature_model_data.id` / `db.creature_template.entry`，发现跨资源占用同一 ID 时输出冲突列表，前端会在资源详情和列表上标注。

## 七、数据一致性约束

### 7.1 ID 关联约束

| 约束 | 说明 |
|------|------|
| `CreatureDisplayInfo.ModelID` → `CreatureModelData.ID` | 必须存在且跨资源唯一 |
| `creature_template.modelid1` → `CreatureDisplayInfo.ID` | 必须一致 |
| `creature_model_info.DisplayID` → `CreatureDisplayInfo.ID` | 必须一致 |
| `creature_template.entry` → `spell.visual_id` | 必须一致 |
| `item_template.spellid_2` → `Spell.ID` | 必须一致 |

### 7.2 业务约束

| 约束 | 说明 |
|------|------|
| `id` 唯一 | 每类资源内部唯一（`{type}-{id:04d}`） |
| DBC 主键唯一 | `spell.id` / `item.id` / `creature_display_info.id` / `creature_model_data.id` 跨资源全局唯一，由 `check_duplicate_resource_ids` 强制 |
| `official_db.name` | 通常必填；当 `tags` 包含 `no_official_data` 时允许为空 |
| `mount_type` 枚举 | 决定 `patch_exporter.SPELL_PROFILES` 中选择的 Speed/Mechanic 模板 |
| `drop.rate` 范围 | 0.0 ~ 1.0 |

## 八、索引设计

当前 SQLite 表上仅 `model_folder` 显式建索引（见 `ResourceMixin`）。其余筛选与排序通过 Python 在内存中完成（数据规模数千条以内，无需复杂索引）。如未来资源规模显著增长，可补建 `(debug_passed, added)`、`(updated_at)` 等索引。

## 九、与现有 xlsx 列的映射

映射配置外置到 `data/mapping/{type}.mapping.yaml`，便于人工调整。`backend/app/sync/xlsx_import.py` 读取映射，将单元格列号转换为 YAML 字段路径，并在导入时进行类型转换（`bool` / `int` / `float` / `str`）与重复 ID 检查。

### 9.1 坐骑列表.xlsx（字段集合）

| 分组 | YAML 字段路径 | 来源列示例 |
|------|---------------|-----------|
| 基本信息 | `id`, `model_folder`, `preview_image`, `mount_type`, `star_rating`, `subtype`, `debug_passed`, `added` | 序号、模型文件夹、模型图示、坐骑类型、星级、子类、调试通过、已添加 |
| 掉落 | `drop.entry`, `drop.instance`, `drop.boss`, `drop.rate` | entry、副本、boss、掉率 |
| 官方信息 | `official_db.name`, `official_db.spell_icon_name`, `official_db.icon_name` | 坐骑名称、技能图标、图标 |
| DBC | `dbc.creature_model_data.*`, `dbc.creature_display_info.*`, `dbc.spell.*`, `dbc.item.*` | CreatureModelData / CreatureDisplayInfo / Spell / Item 列段 |
| 数据库 | `db.creature_template.*`, `db.creature_model_info.*`, `db.item_template.*` | creature_template / creature_model_info / item_template 列段 |

> 当前阶段 `dbc.spell` 仅保留 `id` / `visual_id` / `icon_id` / `name` / `description` 等关键字段；速度、Mechanic 等字段由 `patch_exporter` 按 `mount_type` 注入 `SPELL_PROFILES` 模板，无需在 YAML/Excel 中维护。

### 9.2 映射配置示例

```yaml
# data/mapping/mount.mapping.yaml
sheet_index: 0
header_row: 0
columns:
  1: id
  2: model_folder
  # ...
  9: drop.entry
  10: drop.instance
  # ...
  13: official_db.name
transform:
  debug_passed:
    type: bool
    true_values: ["Y", "y", "是", "1", "true"]
    false_values: ["N", "n", "否", "0", "false", ""]
  drop.rate:
    type: float
```

宠物 / NPC 的映射结构与坐骑一致，仅扩展字段不同（`rarity` 替代 `mount_type` 等）。

## 十、Schema 设计原则

1. **单一职责**：每个 YAML 文件只描述一个资源。
2. **显式优于隐式**：关键字段都显式声明；可选字段允许 `null`，由 `model_validator` 把空字符串/`0`（仅 `str | None`）归一化为 `None`。
3. **分层清晰**：`drop` / `official_db` / `dbc` / `db` 分层明确，与 DBC 文件和 AzerothCore 表一一对应。
4. **命名一致**：YAML 字段使用 snake_case；个别字段（`Item.class`、`item_template.Quality` 等）保留原大小写以与 DBC/SQL 对齐，通过 Pydantic `alias` 映射。
5. **强类型**：`backend/app/schemas/` 下每个子结构都是 Pydantic 模型，避免 `dict[str, Any]` 造成的运行时错误。
6. **可演进**：所有 DBC/SQL 模型基类 `extra="ignore"`，兼容上游字段裁剪；新增字段不破坏旧 YAML。

## 十一、数据迁移策略

### 11.1 首次迁移（已完成）

1. 读取 `坐骑列表.xlsx`、`宠物列表.xlsx`、`NPC列表.xlsx`。
2. 根据 `data/mapping/*.mapping.yaml` 列号到字段名映射，生成初始 YAML 文件。
3. 建立 `data/registry.json` 索引。
4. 写入 SQLite 缓存（`raw_yaml` 整段保存）。
5. 人工抽样校验，使用 `resource validate` 批量复核。

### 11.2 后续维护

- **系统为唯一数据源**：所有资源修改通过 REST API、Web UI、CLI 或直接写 YAML 完成。
- **YAML → SQLite**：`resource_store.save_resource()` 在写入 YAML 后同步更新 SQLite 行；导入 / 启动时也会触发全量同步。
- **Wowhead / wago.tools 补全**：使用 `wowhead lookup-*` / `wago search` / `wago download` 查询并补齐 `official_db.*` 与图标，配合 `enrich-*-data` Skill 半自动化。
- **xlsx 导出**：当前阶段未实现；如需对外导出，可基于 `data/mapping/*.yaml` 反向生成。

## 十二、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| xlsx 列号与 schema 不一致 | 导入数据错位 | 映射配置外置，导入后 `validate` 自动校验；导入后 `.xlsx` 不再作为同步来源 |
| YAML 文件数量大 | 文件系统压力 | 按类型分子目录，使用 `registry.json` 索引；`{id:04d}-{model_folder}.yaml` 命名稳定 |
| 大图片目录访问慢 | 预览卡顿 | 缩略图缓存 + 懒加载目录树 + 按需定位 `model_folder` |
| 多用户并发修改 | Git 冲突 | YAML 纳入 Git，通过合并解决冲突 |
| SQLite 与 YAML 不同步 | 数据不一致 | 所有写操作先写 YAML，再同步 SQLite；`resource_store` 统一入口 |
| DBC 主键跨资源冲突 | 资源互斥 | `check_duplicate_resource_ids` + `patch build` 双重检测 |
| 上游 DBC/SQL 字段变更 | 模型过期 | Pydantic `extra="ignore"`；升级 `wow-dbc-tool` schema 时同步更新模型 |

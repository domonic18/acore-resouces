# 整体架构设计

## 一、设计目标

基于 `docs/requirement/资源管理系统需求v1.0.md`，本系统需要满足：

1. **本地优先**：在开发者本地机器上运行，无需远程服务。
2. **人机双友好**：既提供桌面图形界面，又提供 Agent 可读的 YAML/JSON 和可调用的 CLI 工具。
3. **模型与贴图渲染**：支持直接查看 `.blp` 贴图，并逐步支持 `.m2` 模型 3D 预览。
4. **数据迁移**：将现有 `.xlsx` 清单一次性导入为结构化数据（YAML + SQLite）；后续系统为唯一数据源。
5. **工作流闭环**：从资源定义 → DBC 修改脚本 → SQL 补丁 → 同步到测试/生产环境。
6. **统一技术栈**：减少异构语言与工具链，降低维护成本。

### 2.2 核心决策

- **为什么不直接用 Tauri？**  
  Tauri 更轻量，但本系统核心后端依赖 Python（`wow-dbc-tool`、FastAPI、Pillow），Electron 对 Python 子进程的托管和调试更成熟。若后续打包体积成为瓶颈，可评估迁移到 Tauri。

- **为什么保留 YAML/JSON 文件作为主存储？**  
  Git 友好、Agent 可读、无需数据库即可工作，与 `.xlsx` 形成"人看 Excel，机器读 YAML"的互补。

- **为什么把 `wow-dbc-tool` 和 `wow-mpq-cli` 放在 `tools/`？**  
  二者是可执行工具，需要独立构建（Python 包 / Rust 二进制），与业务代码隔离；通过 git 子模块锁定版本，避免上游变更影响生产。`wow-dbc-tool` 作为 uv 路径依赖被后端 import，`wow-mpq-cli` 通过 subprocess 调用。

- **为什么把原始 DBC 仓库放在 `data/wow-dbc`？**  
  DBC 是数据而非工具，语义上归 `data/`；与 `acore-update-dbc.sh --local-path` 目录结构自然对齐。详见 `docs/arch/07DBC维护与同步方案.md`。

### 3.1 资源文件目录规划

原始资源（`mounts/`、`pets/`、`npcs/`、`icons/`）和一次性 `.xlsx` 导入源不再直接散落在仓库根目录，而是统一归入 `sources/` 和 `imports/`：

| 目录 | 内容 | 是否入 Git | 说明 |
|------|------|:----------:|------|
| `sources/mounts/` | 坐骑预览图、原始 `.m2`、`.blp` | ❌ | 按 `<模型名><中文名>` 组织子目录 |
| `sources/pets/` | 宠物预览图、原始 `.m2`、`.blp` | ❌ | 同上 |
| `sources/npcs/` | NPC 预览图、原始 `.m2`、`.blp` | ❌ | 同上 |
| `sources/icons/` | 游戏图标 `.blp` 与索引 `icon_inv.txt` / `icon_spell.txt` | ❌ | 保留 `interface/icons/` 子目录结构 |
| `imports/` | `坐骑列表.xlsx`、`宠物列表.xlsx`、`NPC列表.xlsx` | ❌ | 一次性导入源，导入后不再反向同步 |
| `data/resources/` | 单资源 YAML | ✅ | 资源定义主存储 |
| `data/mapping/` | xlsx 列映射 | ✅ | 导入时使用 |
| `data/sql/azerothcore-updates/` | 后端生成的 SQL 补丁 | ✅（软链接除外） | 通过软链接桥接 `acore-deploy` |
| `data/wow-dbc/` | 原始 DBC 真相源（子模块） | ✅ | 上游 `domonic18/wow-dbc` |
| `workspace/assets/thumbnails/` | BLP 解码后的 WebP 缩略图 | ❌ | 按需生成，可安全删除 |
| `workspace/data/` | SQLite 运行时数据库 | ❌ | 从 YAML 同步生成 |
| `workspace/patch-jobs/` | 单资源补丁原料 + 产物 | ❌ | 由 `patch export` 与 `/build-mount-patch` 共同维护 |
| `workspace/mpq/` | 批次 MPQ 构建产物 | ❌ | 由 `patch build` 输出 |
| `workspace/dist/` | 已发布 `patch-zhCN-N.mpq` | ❌ | 由 `patch publish` 输出 |
| `workspace/reports/` | 补丁校验报告 | ❌ | JSON 格式 |
| `workspace/logs/` | 应用日志 | ❌ | 按模块分离 |

这样规划的好处：

1. **根目录清晰**：原始资源与导入源不再与代码、文档、配置混排。
2. **职责单一**：`sources/` 只放暴雪原始素材，`imports/` 只放历史 Excel，`workspace/assets/` 只放运行时生成的缓存，`workspace/data/` 放运行时数据库。
3. **Git 友好**：`sources/`、`imports/`、`workspace/` 统一通过 `.gitignore` 排除，避免误提交大文件。
4. **路径可配置**：系统通过配置项 `SOURCES_DIR`、`IMPORTS_DIR`、`ASSETS_DIR` 定位，迁移期可临时指回根目录。

## 五、部署架构

### 5.1 开发环境

```
开发者机器
   ├── acore-resouces/            # 本系统
   │   ├── apps/desktop/          # Electron 桌面外壳
   │   ├── apps/web/              # React 前端（也可独立运行）
   │   ├── backend/               # FastAPI + Typer CLI
   │   ├── tools/wow-dbc-tool/    # 子模块：DBC 读写
   │   ├── tools/wow-mpq-cli/     # 子模块：MPQ 打包
   │   ├── data/                  # YAML 资源 + 子模块 DBC + 生成的 SQL
   │   ├── workspace/             # 运行时数据与缓存（patch-jobs/mpq/dist/reports）
   │   ├── sources/               # 原始资源（mounts/pets/npcs/icons）
   │   └── imports/               # 一次性 xlsx 导入源
   │
   └── acore-deploy/              # 部署项目（消费方）
       ├── data/dbc/              # 由 acore-resouces 同步过来
       └── scripts/acore-update-dbc.sh / acore-update-db.sh
```

开发时可直接启动：

```bash
# 后端（在 backend/ 目录或通过 Electron 拉起）
uv run --project backend uvicorn app.main:app --reload --port 8000

# 前端开发服务器
npm run dev:web    # 等于 cd apps/web && npm run dev

# 桌面应用（开发模式，内部加载 React 前端 + 启动 Python 后端）
npm run dev:desktop
```

后端 CLI 入口为 `uv run --project backend python -m app.cli`（详见 `docs/arch/03Agent交互架构.md`）。

### 5.2 生产/分发形态

```
Electron 应用包
   ├── 前端构建产物 (apps/web/dist → backend/app/static)
   ├── Python 运行时 + backend 依赖 (venv/)
   ├── wow-mpq-cli 二进制
   ├── 启动脚本：spawn Python FastAPI → waitForBackend → 加载前端
```

## 六、演进路线

> 截至 2026-07，Phase 1/2/3 已基本落地；后续工作集中在数据补全、Skill 工作流打磨与发布渠道。

### Phase 1：数据迁移与基础 CRUD ✅

- ✅ 搭建 Python FastAPI 后端 + SQLite（`backend/app/main.py`）。
- ✅ 实现 `xlsx_import.py` 将 `.xlsx` 一次性导入为 YAML + SQLite。
- ✅ 实现基础资源 CRUD、搜索、筛选、排序、分页（`api/resources.py`、`cli/resource.py`）。
- ✅ CLI：`resource list/get/update/delete/validate`、`xlsx import`。
- ⛔ `xlsx export` 导出展示能力已取消：系统作为唯一数据源，不再回写 `.xlsx`。

### Phase 2：预览与可视化 ✅

- ✅ BLP 贴图/图标预览（Pillow 解码 + WebP 缓存，`preview/blp_decoder.py`、`thumbnail_cache.py`）。
- ✅ M2 文件级元数据读取（Python `struct` 解析，`preview/m2_reader.py`）+ 资源目录树（`api/files.py`）。
- ✅ Wowhead / wago.tools 数据补全 CLI（`cli/wowhead.py`、`cli/wago.py`）。

### Phase 3：桌面应用、3D 渲染与工作流闭环 🚧

- ✅ Electron 桌面外壳封装后端和前端（`apps/desktop/`）。
- ✅ 前端 Three.js 原生 M2 渲染（`apps/web/src/components/viewer/`）。
- ✅ 补丁任务导出 / 构建 / 发布三段式工作流（`patch export` → `/build-mount-patch` Skill → `patch publish`）。
- ✅ DBC 子模块化（`data/wow-dbc`）+ SQL 直写 `data/sql/azerothcore-updates/`（软链接到 `acore-deploy`）。
- 🚧 持续完善：宠物 / NPC 补丁、`deploy sync-dbc` 一键同步命令、补丁版本管理、一键 diff 预览与版本 tag。

## 七、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| Electron 打包 Python 依赖体积大 | 安装包过大 | 改为运行时检测系统 Python 并通过 `uv` 安装依赖；或后续评估 Tauri。 |
| `.xlsx` 列号/字段名映射变化 | 一次性导入错位 | 映射配置外置到 `data/mapping/`，导入后 `validate` 自动校验；导入后 `.xlsx` 不再作为同步来源。 |
| 大图片目录访问慢 | 预览卡顿 | 缩略图缓存 + 懒加载目录树 + 按需定位 `model_folder`。 |
| 多人同时修改冲突 | 数据丢失 | 所有 YAML 文件纳入 Git，通过 Git 合并解决冲突。 |
| `wow-dbc-tool` / `wow-mpq-cli` 上游变更影响生产 | 补丁构建失败 | 二者锁定为 git 子模块，版本可控；升级走独立 PR。 |
| DBC 记录 ID 跨资源冲突 | 资源互斥 | `resource validate` 与 `patch build` 都会检测冲突，冲突时拒绝构建。 |

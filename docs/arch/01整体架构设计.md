# 整体架构设计

## 一、设计目标

基于 `docs/requirement/资源管理系统需求v1.0.md`，本系统需要满足：

1. **本地优先**：在开发者本地机器上运行，无需远程服务。
2. **人机双友好**：既提供桌面图形界面，又提供 Agent 可读的 YAML/JSON 和可调用的 CLI 工具。
3. **模型与贴图渲染**：支持直接查看 `.blp` 贴图，并逐步支持 `.m2` 模型 3D 预览。
4. **数据迁移**：将现有 `.xlsx` 清单一次性导入为结构化数据（YAML + SQLite）；后续系统为唯一数据源，仅保留导出到 `.xlsx` 的能力。
5. **工作流闭环**：从资源定义 → DBC 修改脚本 → SQL 补丁 → 同步到测试/生产环境。
6. **统一技术栈**：减少异构语言与工具链，降低维护成本。

## 二、技术选型

### 2.1 统一技术栈

| 层级 | 技术选型 | 说明 |
|------|---------|------|
| **桌面外壳** | Electron 33+ | 本地窗口、菜单、文件系统访问；启动时托管 Python 后端。 |
| **后端** | Python 3.11+ | 与 `wow-dbc-tool` 同生态，可直接复用 DBC 操作能力。 |
| | FastAPI 0.110+ | 高性能异步 Web 框架，自动生成 OpenAPI。 |
| | SQLAlchemy 2.0+ | ORM，本地使用 SQLite，未来可切 PostgreSQL。 |
| | Pydantic 2.5+ | 数据校验和序列化。 |
| | Typer 0.12+ | 类型安全的 CLI 构建。 |
| | Pillow 10+ | 原生读写 `.blp` 贴图。 |
| | PyYAML / jsonschema | YAML 读写和 Schema 校验。 |
| **前端** | React 18.3+ + TypeScript | Electron 内嵌 UI 框架。 |
| | Vite 5.0+ | 构建工具，支持桌面应用内嵌前端的开发热更新。 |
| | shadcn/ui + Tailwind CSS | UI 组件库。 |
| | Three.js 0.160+ | 3D 模型查看器。 |
| | TanStack Query 5+ | 服务端状态管理。 |
| **模型转换** | Rust `warcraft-rs` | 封装为独立 CLI `tools/model-converter`，将 `.m2` + `.blp` 转为 `.glb`/`.gltf`。 |
| **数据存储** | YAML/JSON 文件 | 资源定义主存储，纳入 Git。 |
| | SQLite 3.40+ | 运行时查询、筛选、统计。 |
| | 原始 `.xlsx` | 一次性导入源和导出展示用，不纳入 Git。 |
| **测试** | pytest（后端） + vitest（前端） + Playwright（e2e） | 与参考项目 SquadSight / Keira3 对齐。 |
| **部署** | Docker Compose（可选） | 仅用于开发环境隔离，生产形态为 Electron 桌面应用。 |

### 2.2 核心决策

- **为什么不直接用 Tauri？**  
  Tauri 更轻量，但本系统核心后端依赖 Python（`wow-dbc-tool`、FastAPI、Pillow），Electron 对 Python 子进程的托管和调试更成熟。若后续打包体积成为瓶颈，可评估迁移到 Tauri。

- **为什么保留 YAML/JSON 文件作为主存储？**  
  Git 友好、Agent 可读、无需数据库即可工作，与 `.xlsx` 形成“人看 Excel，机器读 YAML”的互补。

- **为什么要用 Rust 做模型转换？**  
  `warcraft-rs` 对 WoW M2/BLP 格式的解析和转换支持最成熟，远超 Python/JS 生态中的现有库。将其封装为 CLI 工具，Python 通过 subprocess 调用，保持主栈简洁。

### 3.1 资源文件目录规划

原始资源（`mounts/`、`pets/`、`npcs/`、`icons/`）和一次性 `.xlsx` 导入源不再直接散落在仓库根目录，而是统一归入 `sources/` 和 `imports/`：

| 目录 | 内容 | 是否入 Git | 说明 |
|------|------|:----------:|------|
| `sources/mounts/` | 坐骑预览图、原始 `.m2`、`.blp` | ❌ | 按 `<模型名><中文名>` 组织子目录 |
| `sources/pets/` | 宠物预览图、原始 `.m2`、`.blp` | ❌ | 同上 |
| `sources/npcs/` | NPC 预览图、原始 `.m2`、`.blp` | ❌ | 同上 |
| `sources/icons/` | 游戏图标 `.blp` | ❌ | 保留 `interface/icons/` 子目录结构 |
| `imports/` | `坐骑列表.xlsx`、`宠物列表.xlsx`、`NPC列表.xlsx` | ❌ | 一次性导入源，导入后不再反向同步 |
| `assets/thumbnails/` | BLP 解码后的 WebP 缩略图 | ❌ | 按需生成，可安全删除 |
| `assets/gltf/` | M2 转换后的 glTF 模型 | ❌ | 按需生成，可安全删除 |

这样规划的好处：

1. **根目录清晰**：原始资源与导入源不再与代码、文档、配置混排。
2. **职责单一**：`sources/` 只放暴雪原始素材，`imports/` 只放历史 Excel，`assets/` 只放运行时生成的缓存。
3. **Git 友好**：`sources/`、`imports/`、`assets/` 统一通过 `.gitignore` 排除，避免误提交大文件。
4. **路径可配置**：系统通过配置项 `SOURCES_DIR`、`IMPORTS_DIR`、`ASSETS_DIR` 定位，迁移期可临时指回根目录。

### 4.2 模块划分

| 模块 | 职责 | 对应代码/目录 |
|------|------|--------------|
| 资源管理模块 | 资源的 CRUD、筛选、搜索、校验 | `backend/app/services/resources.py` |
| xlsx 导入/导出模块 | `.xlsx` 一次性导入和导出展示 | `backend/app/sync/xlsx_import.py`、`xlsx_export.py` |
| DBC 导出模块 | 根据资源定义生成 `wow-dbc-tool` Python 脚本 | `backend/app/exporters/dbc.py` |
| SQL 导出模块 | 根据资源定义生成 SQL 补丁 | `backend/app/exporters/sql.py` |
| 预览服务模块 | BLP 解码、M2 文件清单、glTF 缓存 | `backend/app/preview/` |
| 工作流引擎 | 编排校验 → diff → 导出 → 调用外部脚本 | `backend/app/services/workflow.py` |
| Agent 接口模块 | CLI 工具集 | `backend/app/cli/` |
| 桌面外壳模块 | Electron 主进程、窗口管理、Python 子进程托管 | `apps/desktop/src/main.ts` |

```

   │   ├── apps/web/              # React 前端

   │   ├── sources/               # 原始资源（mounts/pets/npcs/icons）
```

开发时可直接启动：

```bash
# 后端
uvicorn backend.app.main:app --reload --port 8000

# 桌面应用（开发模式，内部加载 React 前端）
cd apps/desktop && npm run dev
```

`apps/web` 为 Electron 内嵌的 React 前端代码，不单独作为浏览器页面发布。

### 5.2 生产/分发形态

```
Electron 应用包
   ├── 前端构建产物 (dist/)
   ├── Python 运行时 + backend 依赖 (venv/)
   ├── model-converter 二进制
   ├── 启动脚本：启动 Python FastAPI，然后加载前端
```

## 六、演进路线

### Phase 1：数据迁移与基础 CRUD

- 搭建 Python FastAPI 后端 + SQLite。
- 实现 `xlsx_import.py` 将 `.xlsx` 一次性导入为 YAML + SQLite。
- 实现 `xlsx_export.py` 将资源导出为 `.xlsx` 供人工查看。
- 实现基础资源 CRUD、搜索、筛选。
- 实现 CLI：`resource list/get/update`、`xlsx import`、`xlsx export`、`validate`。

### Phase 2：预览与可视化

- BLP 贴图/图标预览（Pillow 解码 + WebP 缓存）。
- M2 文件级元数据读取（pywowlib）+ 文件树展示。
- Rust `model-converter` PoC：将示例 `.m2` 转为 glTF。
- React 前端接入 Three.js 查看器。

### Phase 3：桌面应用与工作流闭环

- Electron 桌面外壳封装后端和前端。
- DBC/SQL 补丁导出集成。
- 一键 diff 预览、版本 tag、调用外部 `acore-update-*` 脚本。

## 七、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| `warcraft-rs` 对 3.3.5a M2 转换支持不完善 | 3D 预览不可用 | 保留 Phase 1/2 降级方案；先用示例模型做 PoC。 |
| Electron 打包 Python 依赖体积大 | 安装包过大 | 改为运行时检测系统 Python 并安装依赖；或后续评估 Tauri。 |
| `.xlsx` 列号/字段名映射变化 | 一次性导入错位 | 映射配置外置到 `data/mapping/`，导入后自动校验；导入后 `.xlsx` 不再作为同步来源。 |
| 大图片目录访问慢 | 预览卡顿 | 缩略图缓存 + 懒加载 + 按需定位 `model_folder`。 |
| 多人同时修改冲突 | 数据丢失 | 所有 YAML 文件纳入 Git，通过 Git 合并解决冲突。 |

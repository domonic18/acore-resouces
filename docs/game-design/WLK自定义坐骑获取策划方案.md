# WLK 自定义坐骑获取策划方案

> 状态：设计稿（待评审）
> 适用：`acore-resoures` 坐骑/宠物资源库 + AzerothCore 3.3.5a 测试服
> 数据基线：本地 `acore_world` 实测（2026-11-22，docker `acore-mysql`）+ nfuwow 3.3.5 库交叉核对
> 本文取代 2026-09-11 的《坐骑 WLK 副本掉落规划（调研数据源）》：该稿的副本清单混入 BC 副本、尾王译名与本库不符，且未区分「BOSS 直掉 / 宝箱」两种奖励来源。

---

## 1. 背景与目标

`acore-resoures` 已录入 **430 只坐骑**（其中 333 只 `added: false` 待启用）和 **107 只宠物**（全部未启用）。这些资源目前只是「可浏览的模型库」，没有游戏内获取路径，玩家感知不到。

本方案把 WLK 副本做成投放场景，用两条路径消耗这些资源：

1. **副本尾王直掉** — 给 WLK 无官方坐骑奖励的副本配一只自定义坐骑，作为副本的「稀有目标」。
2. **日常任务盲盒** — 给 WLK 日常任务配奖励包，开包有极小概率出坐骑/宠物，制造回访动机。

两条路径互补：尾王是「一次性里程碑」，日常是「高频随机」，共同服务于提升游戏黏性的目标。

## 2. 设计约束（已定规则）

| # | 规则 | 说明 |
|---|------|------|
| R1 | 一个 BOSS 配一个坐骑 | 沿用现有 `DropInfo` 单来源结构，不扩展多来源 schema |
| R2 | 掉落难度必须是英雄 | 通过 `creature_template.difficulty_entry_N` 变体实现 |
| R3 | **禁止用 LootMode 表达难度** | AC 的 `LootMode` 是「遭遇变体」位掩码（`LOOT_MODE_HARD_MODE_1..4`），不是难度；`LootMgr.cpp:1695` 走 `item->lootmode & lootMode` 过滤 |
| R4 | 掉率参考既有 TBC 基线 | 英雄 5 人本 `0.02` / 团本 `0.03` / 普通 5 人本 `0.01` |
| R5 | 有官方坐骑奖励的副本不再添加 | 本次只覆盖「无官方坐骑」的副本 |
| R6 | YAML 是唯一真相源 | 逐个坐骑分析后显式写入，不做规则化批量改写 |

### 3.4 既有投放占用与排除口径（R7）

**「已投放」的判定**（三条任一命中即算已投放，本方案一律不选）：

1. YAML `added: true` —— 库内 97 只（74 只带 `drop` 块 + 23 只投放来源不在 `drop` 块内，见下表）；
2. YAML `drop` 块非空 —— 库内 75 只，其中 74 只与条件 1 重合，另有 #36「黄鬃熊坐骑」已配玛拉顿·瑟莱德丝公主的投放但尚未 `added: true`，同样视为已占用；
3. 模型文件（`dbc.creature_model_data.model_name`）已被已投放坐骑占用 —— 属同一模型的重复款，同样排除（见末表）。

空闲池 = 430 − 97（已投放）− 1（#36 已配投放未启用）= **332 只**。

**核对维度**：坐骑 `id` / 模型文件 / 物品 entry / 库内 `drop` 占用 / 线上 `acore_world` 掉落源，五个维度逐项比对。

**结论**：§4 的 13 只、§5 的 4 只、§6.3 盲盒的 6 只，合计 **23 只全部落在 332 只空闲池内**（`added: false` 且 `drop` 块为空），与 97 只已投放坐骑在上述五个维度**零冲突**；线上库中这 23 只的物品 entry 也均无任何掉落源。唯一需要注意的是其中 4 只（93671 / 123890 / 143638 / 163042）的物品行已存在于测试服 `item_template`，但没有掉落源，导出时按 DELETE+INSERT 覆盖即可，无副作用。

**本次复核实际拦下的 1 例**：盲盒池原候选 #323「地狱咆哮战龙」的模型 `KorKronProtodrakeMount.m2` 与已投放的 #324「迦拉卡斯的子嗣」（海加尔峰·阿兹加洛）同源，触发 R7 → 已换成 #415「装甲啸天龙」（见 §6.3）。其余 22 只复核通过。

### 5.1 团本难度变体的实测口径

结论来自 **AC 服务端源码 + 冰冠堡垒掉落表结构**双向验证：

- AC `Creature::InitEntry`（`src/server/game/Entities/Creature/Creature.cpp`）按 spawn mode 选模板：
  `diff = GetMap()->GetSpawnMode()`，从 `diff` 递减取 `DifficultyEntry[diff-1]`；`diff >= RAID_DIFFICULTY_10MAN_HEROIC` 且是团本时 `diff -= 2` 回退。
- AC `DBCEnums.h` 的 raid spawn mode 枚举：`0 = 10 人普通`、`1 = 25 人普通`、`2 = 10 人英雄`、`3 = 25 人英雄`。

| 变体列 | 实际难度 | 验证依据 |
|--------|----------|----------|
| 基础 entry | 10 人普通 | spawn mode 0 直接用基础模板；巫妖王 36597 → ref 34238（T10 **10 人**武器，ItemLevel 258）+ T9 头盔代币 40616/40617/40618（10 人 ICC 属 T9 阶段） |
| `difficulty_entry_1` | 25 人普通 | spawn mode 1 → `DifficultyEntry[0]`；巫妖王 39166 → ref 34250（T10 **25 人**武器，ItemLevel 271）+ T10 代币 52025/52026/52027 |
| `difficulty_entry_2` | 10 人英雄 | spawn mode 2 → `DifficultyEntry[1]`；巫妖王 39167 → ref 34262（10 人武器的英雄版，ItemLevel 271）；纳克萨玛斯 / 奥杜尔无 d2 |
| `difficulty_entry_3` | 25 人英雄 | spawn mode 3 → `DifficultyEntry[2]`；巫妖王 39168 → ref 34274（ItemLevel 284）+ 英雄代币 52028-52030，且 50818 无敌的缰绳 100% 挂在此表（零售即 25 人英雄专属） |

**回退规则的实际影响**：

- 533 纳克萨玛斯、603 奥杜尔、616 永恒之眼、624 阿尔卡冯都只有 `difficulty_entry_1`（25 人普通）。25 人英雄实例（spawn mode 3）取不到 d3 → `diff` 减 2 回到 1 → 落到 `difficulty_entry_1`，所以**25 人普通与 25 人英雄共用同一张 loot 表**。

- 615 黑曜石圣殿是 10 人副本，25 人难度不存在；28860 / 31311 分别是 10 人普通 / 25 人普通（后者实际不生效）。

**刷怪行（`creature.spawnMask`）实测**：631 冰冠与 724 红玉为 `15`（四种难度全含，英雄实例有尾王）；533 / 603 / 615 全为 `3`（仅 10 人普通 + 25 人普通），**英雄难度下这些副本可能根本没有尾王刷怪行**。

## 7. 落地实现要点

### 7.1 掉落表写入机制

现有导出器（`backend/app/services/patch_exporter.py`）对 `DropInfo` 的处理：

```python
tables.append(SQLPlanTable(
    name="creature_loot_template",   # 或 gameobject_loot_template
    operation="insert",
    records=[{
        "Entry": int(drop.entry),      # 掉落表 id（= 英雄变体 creature entry）
        "Item": item_entry,            # 坐骑物品 entry
        "Reference": 0, "Chance": round(drop.rate * 100, 4),
        "QuestRequired": 0, "LootMode": 1,
        "GroupId": 0, "MinCount": 1, "MaxCount": 1,
    }],
))
```

`drop.entry` 语义确认：**它就是 `creature_loot_template.Entry`，不是 creature id**。本库绝大多数 creature 的 `lootid = entry`，所以两者常相等；英雄变体同理（31673 的 `lootid` 就是 31673）。本方案统一填**英雄变体的 lootid**。

### 7.2 YAML 改动示例

```yaml
# data/resources/mounts/0180-GhostlyCharger幽灵军马.yaml
id: 180
added: true
drop:
  source: creature          # 可省略，默认 creature
  entry: 31673              # 掠夺者因格瓦尔(英雄变体)的 loot 表 id
  instance: 乌特加德城堡(英雄模式)
  boss: 掠夺者因格瓦尔
  rate: 0.02
```

### 7.3 注意事项清单

1. **难度只能靠变体表**：`drop.entry` 填英雄变体 lootid，不要试图用 `LootMode` 表达难度（R3）。
2. **616 需要先补 `lootid`**：28859 / 31734 的 `lootid` 现为 0，需先写入非零值并建对应 `creature_loot_template`，否则坐骑无处可挂。
3. **578 / 616 建议先补官方宝箱**（§3.3），符合 R5；本方案的自定义坐骑作为「不补官方」时的备选。
4. **668 需确认脚本 spawn**：辛达苟萨无 `creature` 行，需确认 `boss_sindragosa` 的 spawn 是否同样走难度变体解析。
5. **物品 entry 冲突**：本方案选用的 23 只坐骑物品 entry 均 ≥ 91000（自定义段）。库内另有 87 只坐骑沿用零售 item entry（如 44151 蓝色始祖幼龙缰绳、76902 幽灵驭风者、43953 蓝色幼龙缰绳），**本方案不启用其中任何一只**，启用会 `DELETE`+`INSERT` 覆盖官方物品行 —— 若后续启用必须逐个核对。
6. **贴图变体**：若后续启用与已上线坐骑共用模型的坐骑，必须使用不同 `texture_variation` 区分。本方案涉及的同模型兄弟款（#333/#334/#335、#421/#423、#92/#93、#102/#104/#105）目前**全部未投放**，启用时在兄弟款之间用不同贴图变体即可。
7. **R7 落地前再核一次**：`added` 与 `drop` 会被其它批次改动，落地当天需重新跑一遍 §3.4 的五维度核对（尤其「同模型词干」这一条，它能抓到 id 与模型名都不同的同源款）。
8. **逐个落地**：遵循「逐个分析、YAML 显式值为准」约定，走「模型/贴图 → YAML 补全 → drop 配置 → validate_job」流程，不批量改写。
9. **未登记模型不自行补 YAML**：`sources/` 未入库的模型不擅自上线。
10. **团本英雄实例可能无尾王**：533 / 603 / 615 的刷怪行 `spawnMask` 均为 `3`（不含英雄难度位）。这三本的坐骑表挂上后，英雄实例里可能根本打不到尾王 —— 先在测试服确认，必要时补刷怪行或改挂 25 人普通表。
11. **533 / 603 / 616 的 25 人英雄与普通共用一表**：这三个尾王没有 `difficulty_entry_3`，英雄实例回退到 `difficulty_entry_1`。若要「只掉 25 人英雄」，需补 d3 模板 + 独立 loot 表。
